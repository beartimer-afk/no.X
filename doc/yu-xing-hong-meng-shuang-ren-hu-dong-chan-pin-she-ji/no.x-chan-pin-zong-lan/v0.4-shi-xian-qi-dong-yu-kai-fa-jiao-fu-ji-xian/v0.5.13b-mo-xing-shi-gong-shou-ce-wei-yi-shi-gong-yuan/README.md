# v0.5.1｜3B 模型施工手册（唯一施工源）

> 本章不是给高级工程师阅读的架构建议，而是给**低推理能力开发模型**执行的施工说明。

## 目标

让一个约 3B 规模、容易漏要求、容易自作主张、跨上下文能力有限的开发模型，也可以在**不重新做产品设计、不重新做 UI 决策、不自行补规则**的前提下，实现 NO.X v0.1。

## 文档设计原则

1. **重复优于引用。** 每个原子任务重复写关键颜色、尺寸、状态与禁止项。
2. **一步一验证。** 每个任务完成后必须产出指定截图/录屏，再进入下一任务。
3. **不能猜。** 未定义内容必须输出 `SPEC_GAP`，停止该点实现。
4. **不能优化。** “更符合平台规范”“我认为更好看”“顺手重构”均不是合法修改理由。
5. **不能提前实现。** 当前任务未要求的功能，即使文档后面存在，也不得提前加入。
6. **只能机械施工。** 开发模型的工作是编码、运行、截图、修复；不是产品经理、UI 设计师或游戏设计师。

## 权威优先级

发生冲突时按以下顺序执行：

1. 本章 v0.5 当前原子任务包中的明确值
2. v0.4 强约束实现合同
3. v0.3 UI 设计系统
4. v0.2 产品逻辑
5. 视觉附录图片
6. 开发模型个人判断（仅在前五层都没有定义时，且必须先报告 `SPEC_GAP`）

## v0.1 冻结范围

本轮只实现以下完整链路：

**Home → Round Ready → Bomb 按住/说话 → PASS → 对方继续 → Tension/Fake Signal → Explosion → Lose Reveal → Challenge Reveal → 下一轮。**

明确不做：Secret Match、账号、联网、多人、排行榜、媒体拍摄、录音识别、AI 内容生成、远程内容包、复杂设置、商店、付费。

## 固定平台

* HarmonyOS 手机应用
* ArkTS + ArkUI
* 竖屏优先
* v0.1 禁止横屏重新布局
* 单机运行
* 所有挑战文本来自本地静态数据

## 完成定义

只有同时满足以下条件，才算 v0.1 完成：

* 从冷启动可完整玩至少 5 轮；
* 不出现流程断裂；
* Bomb 按压手感符合合同；
* Explosion 无明显掉帧；
* UI 截图通过固定清单；
* 核心颜色、间距、尺寸没有擅自修改；
* 所有 `SPEC_GAP` 已被关闭或明确延期。
