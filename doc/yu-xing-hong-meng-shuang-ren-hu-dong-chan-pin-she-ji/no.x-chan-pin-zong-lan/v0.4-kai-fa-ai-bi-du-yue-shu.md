# v0.4｜开发 AI 必读约束

{% hint style="danger" %}
**这是实现合同，不是参考建议。** 开发 AI 的职责是忠实实现，不是重新做产品设计。未经产品负责人明确修改本文档，禁止任何“更合理”“更现代”“更符合平台习惯”“我认为更好”的主动改动。
{% endhint %}

## 1. 权威顺序

发生冲突时，必须按以下顺序执行：

1. **v0.4 强约束实现合同**
2. **v0.3 UI 设计系统与高保真规格**
3. **v0.2 核心玩法与产品规格**
4. **附录视觉探索图**
5. 开发者 / AI 自己的判断

第 5 项只有在前 4 项完全没有定义时才允许出现，并且必须先标记 `SPEC_GAP`，不得静默补设计。

## 2. 禁止自行修改的内容

以下内容全部视为冻结：

* 品牌名 `NO.X`；
* 中文界面为第一实现语言；
* 暗黑 + 暗紫 + 霓虹粉 / 紫视觉；
* 小圆形发光 Core 是 Bomb 主交互；
* **按住 Core + 同时回答 + 随时可能爆炸** 是核心手感；
* Home → Ready → Pressing → Tense → Lose → Challenge → Next Round 的主流程；
* 页面信息层级、按钮数量、按钮文案、状态文案；
* v0.4 中写明的颜色、尺寸、圆角、边距、字号、动画时长、触觉和声音事件；
* 不得把 Core 改成卡通炸弹、爱心炸弹、实体炸弹插画；
* 不得加入顶部 Tab、底部 Tab、抽屉导航、排行榜、聊天、账号、社交、多人房间；
* 不得主动增加弹窗、Toast、说明页、引导页；
* 不得把成人挑战改写成普通聚会题库；
* 不得为了“过审”在客户端制作隐藏成人开关或审核差异逻辑。

## 3. 禁止“优化”

以下说法不能成为偏离规格的理由：

* “为了更符合 HarmonyOS 规范”；
* “为了提高可用性我把按钮移了一下”；
* “为了响应式我重新排版”；
* “这个颜色对比不够所以我换了”；
* “我觉得这个动效太慢”；
* “这个文案可以更自然”；
* “为了组件复用我把两个页面合并”；
* “为了开发简单先用默认组件”。

如实现困难，必须保留视觉结果并更换技术方案，而不是降低设计标准。

## 4. 缺失信息处理

遇到文档未定义的细节：

1. 先查 v0.4；
2. 再查 v0.3；
3. 再查 v0.2；
4. 再查附录视觉图；
5. 仍无答案，输出 `SPEC_GAP: <问题>`；
6. 使用**最小中性实现**临时占位，不新增视觉语言；
7. 占位必须集中在常量 / Token 中，方便替换。

## 5. UI 验收原则

“功能可用”不等于完成。每个阶段至少同时满足：

* 页面截图与规格位置一致；
* 字号、间距、圆角、按钮高度一致；
* 无系统默认蓝色、默认绿色、默认灰色按钮渗透；
* 动效时间轴一致；
* 按压交互可重复且不卡顿；
* Explosion 无明显掉帧；
* 暂停 / 前后台切换后状态正确；
* 真机触觉符合事件定义。

## 6. 任何偏离都必须显式列出

每个开发提交必须附：

* `Implemented exactly:` 已完全按规格实现项；
* `SPEC_GAP:` 规格缺口；
* `Deviation:` 与规格不同之处及原因。

没有 `Deviation` 不代表可以静默偏离。
