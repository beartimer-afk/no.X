# 31｜编排者协议：如何逐个驱动 3B 模型施工

本页给“负责调用 3B 开发模型的人/强模型”使用。

## 每个 TASK 前

1. 确认上一个任务人工验收 PASS；
2. 确认 Git 工作区 clean；
3. 保存当前 commit hash；
4. 只读取当前 TASK 页 + 00 执行协议；
5. 不把后续 TASK 页给 3B，避免提前实现；
6. 将第 22 页固定模板与当前 TASK 全文拼接后发送。

## 收到 3B 回复后先看什么

按顺序检查：

1. `STATUS` 是否为 IMPLEMENTED；
2. `SPEC_GAP` 是否 NONE；
3. `FILES CHANGED` 是否包含任务外文件；
4. `BUILD` 是否有实际执行证据；
5. `ARTIFACTS` 是否齐；
6. `ACCEPTANCE` 是否逐项回答。

任一不满足，**不要进入下一 TASK**。

## 再检查 Git diff

重点查：

* 是否改了 UiTokens；
* 是否新增依赖；
* 是否新增权限；
* 是否改了不在 FILES TO CHANGE 的文件；
* 是否删除已有验收代码；
* 是否把固定文案改写；
* 是否把状态机拆成额外 boolean。

## 再看截图/录屏

不接受仅文字描述。

截图必须来自实际运行 App；不能用设计图代替。录屏必须包括真实点击/长按行为。

## 失败时如何给反馈

反馈必须具体到验收编号：

```
TASK-004 未通过。
A02 FAIL：合法阈值实际约 850ms，规格为 1100ms。
A04 FAIL：UI 出现 0.0–1.0 数字进度，规格禁止。

只修 A02、A04。
禁止修改其他已通过项。
修复后重新提交同名验收素材。
```

不要给模糊反馈：`感觉不对`、`优化一下`、`更漂亮点`。

## 通过时

明确发送：

```
TASK-004 ACCEPTED.
提交 Git commit：NOX TASK-004 press interaction
停止。等待 TASK-005。
```

## 编排者自己也不得擅改规格

如果试玩产生新想法：记录为下一版本变更，不直接塞给正在施工的 3B 模型。
