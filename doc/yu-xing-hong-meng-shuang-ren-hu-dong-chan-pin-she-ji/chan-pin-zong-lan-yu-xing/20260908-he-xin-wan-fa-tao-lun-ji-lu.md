# 2026-09-08｜核心玩法讨论记录

这页保留本轮讨论的思路演变。目的不是只保存最终结论，而是记录为什么做出这些判断，避免未来重新把产品带回已经否定过的方向。

## 1. 起点：寻找“性爱游戏 + 输赢 + 录音录像”的现有产品

最初的设想是寻找可以辅助成年人面对面互动的 App，例如通过游戏决定输家，再让输家执行挑战，挑战可能包含录音、拍照或录像。

调研后发现市场上的产品大多只覆盖其中一部分：

* 有的擅长成人挑战题库；
* 有的擅长随机输赢；
* 有的提供图片 / 视频；
* 有的提供任务完成证明；
* 但很少有产品把“游戏产生输家 → 挑战 → 当场完成 → 验收”做成完整、精致、私密的闭环。

由此产生了最初的产品机会判断：不是再做一个成人 Truth or Dare 题库，而是做一个更完整的互动机制。

## 2. 第一个重要纠正：只有一台手机

用户明确提出：

> “两个一起的时候只有一个手机，不能做成分享的。”

这是第一次关键收敛。

产品不应该建立在：

* 两个人都安装 App；
* 两个账号配对；
* 私聊；
* 分享给对方；
* 云端情侣空间；
* 双手机联动。

真正场景是：**两个人就在一起，共用这一台手机。**

因此 Pass & Play / 轮流拿手机成为基础交互模型。

这也直接催生了 Secret Match：A 私密选择后把手机交给 B，双方只看到共同匹配的结果。

## 3. 审核与产品外层：不能靠伪装，应该真的做成通用引擎

讨论中出现了“为了过审，需要和成人内容无关的外壳”的想法。

随后形成更稳妥的产品判断：

产品不应该是“审核时普通、审核后隐藏解锁另一套成人产品”。真正长期成立的方式是：**App 本身就是通用双人挑战游戏引擎。**

官方能力可以完全正常存在：

* 游戏产生输家；
* 自定义挑战；
* 倒计时；
* 录音；
* 拍照；
* 录像；
* 对方验收；
* 本地隐私；
* 数据包。

成人内容不需要由官方提供。

## 4. 第二个关键结论：成人部分只是数据包

用户明确提出：

> “成人部分只是数据包，用户自定义即可。”

这句话把产品架构彻底理顺。

产品可以拆成：

**Game Engine → Mini Game / Rule → Challenge Pack → User Content**

官方内置的是能力，不是特定成人内容。

用户可以创建任何私人挑战包。普通、情侣、喝酒、搞笑等场景，本质上只是不同数据。

这意味着：

* 核心代码不围绕成人语义设计；
* 内容和机制分离；
* 产品有更大的可扩展性；
* 付费点可以放在创作、规则、媒体、隐私和高级引擎能力上。

## 5. UI 被提升为核心产品能力

用户提出：

> “我觉得这个 app UI 很重要，需要花很多功夫。”

这一判断被确认。

这类 App 如果 UI 普通，很容易变成廉价真心话大冒险；而它真正卖的是现场气氛。

因此 UI 不能只理解为视觉皮肤，而应该承担：

* 神秘感；
* 暧昧 / 私密感；
* 紧张感；
* 结果揭晓；
* 手机交接；
* 秘密内容遮挡；
* 游戏节奏。

尤其 Bomb 这样的玩法，需要声音、震动、动效共同组成完整体验。

## 6. 酒局场景：一个有价值的验证，但差点带偏核心

用户提出：

> “UI 场景可以丢设置里面，其实这个 App 喝酒的时候也能用。谁炸了谁喝，喝酒的人制定下一个挑战……我们之前都是转酒瓶子，没有神秘感。”

这一例子揭示了两个重要东西。

### 6.1 有价值的发现：实体随机工具缺少持续悬念

“转酒瓶子没有神秘感”真正指出的是：

**手机可以把一次瞬间随机，变成一段持续的未知过程。**

例如 Bomb 在两人之间传递，不知道何时爆炸。随着时间增长，压力持续增加。

这比“点击随机按钮马上出结果”更接近真正的游戏体验。

### 6.2 有价值的机制：输家参与创造下一轮

“喝的人制定下一个挑战”不应该只理解为酒局规则。

它提出了一个更普遍的机制：

**本轮输家完成任务后，可以获得下一轮部分控制权。**

这让玩家成为内容创造者，使游戏不再只是 App 单向发牌。

## 7. 第三个重要纠正：酒瓶子把产品带偏了吗？

用户随后主动提出：

> “你看看我说的酒瓶子是不是把核心带偏了。”

结论：**有一点。**

酒瓶子只是一个用来解释“缺少悬念”的现实例子，但讨论一度被带向：

* 多人 Party Game；
* 酒局 App；
* 需要询问人数；
* 玩家排行榜；
* 多人淘汰。

这些都不是当前核心。

因此重新收敛：

> **两个人 + 一台手机 + 用户自定义内容 + 私密挑战游戏引擎。**

喝酒只是其中一个 Pack / 规则预设，不应决定产品信息架构。

## 8. 是否需要知道几个人玩？

讨论中进一步发现：很多基础玩法其实完全不需要 App 知道人数。

例如 Bomb：

* 手机被传递；
* 爆炸时拿着手机的人就是输家；
* 现实中的参与者天然知道当前是谁。

只有出现以下需求时，人数 / 玩家身份才真正有价值：

* 记分；
* 排行；
* 淘汰；
* 指定目标；
* 每人独立任务池；
* 个人长期统计。

由于当前产品重新聚焦双人，第一版不应该提前建设复杂多人系统。

## 9. 场景应该放在设置 / Pack，而不是首页

另一个重要共识是：

> **场景不是产品。**

情侣、酒局、旅行、聚会、搞笑，都只是挑战池和规则的不同组合。

因此首页不应先问“你是什么场景”。

现场 App 更需要极短启动路径：

**打开 → START → 玩。**

Pack / Create / Settings 可以承载内容和高级配置。

## 10. 当前稳定产品公式

将本轮讨论压缩后，形成以下产品公式：

> **不是成人 App，是通用挑战游戏引擎。**
>
> **不是双手机社交，是两个人面对面共用一台手机。**
>
> **App 的核心价值不是题库，而是制造悬念、决定输赢、组织互动。**
>
> **内容全部数据化，因此普通、情侣、喝酒以及私人成人内容都可以运行在同一套机制上。**

## 11. 当前三个最有价值的设计资产

### Secret Match

双方私密做选择，只暴露共同接受集合。既制造神秘感，也降低直接表达拒绝的压力。

### Suspense Engine / 悬念引擎

通过未知时间、随机、震动、声音、动画和节奏，让手机承担实体酒瓶 / 骰子无法完成的“情绪主持”角色。

### Challenge Pack / 用户内容层

规则与内容彻底分离，用户可以自己定义任务。产品能力因此不受单一场景限制。

## 12. 后续设计阶段需要继续回答的问题

这些问题尚未冻结，后续应通过原型和试玩验证：

* Secret Match 在正式开局前做，还是游戏过程中逐步出现？
* Bomb 一局的最佳时长和交互动作是什么？
* “输家决定下一轮”是否会破坏公平感，如何控制权限？
* Challenge 卡片揭晓应一次显示还是分层揭晓？
* 用户创建挑战的编辑器需要多简单，才能在现场临时创建？
* 媒体挑战应放在第一版还是后置？
* UI 应如何同时做到高级、神秘和轻游戏感，而不显得低俗或幼稚？
* 默认 START 是否应做到零配置直接开玩？

这些应作为下一阶段产品设计与试玩验证的主要问题。
