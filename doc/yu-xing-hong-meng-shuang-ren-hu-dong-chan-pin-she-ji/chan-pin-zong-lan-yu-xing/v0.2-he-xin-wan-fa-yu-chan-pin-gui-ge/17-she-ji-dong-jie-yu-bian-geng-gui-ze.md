# 17｜设计冻结与变更规则

## 1. 为什么需要冻结

这个产品非常容易在开发中被“顺手优化”成普通工具：增加倒计时、显示概率、把结果和 Challenge 合并、每页加说明、首页加模式选择。单项看起来合理，组合后会摧毁悬念和节奏。

因此以下内容视为 v0.2 设计冻结。

## 2. 冻结项

* START 默认不问人数；
* Quick Start 不先问场景；
* Bomb 不显示剩余时间/概率/进度；
* Lose Reveal 与 Challenge Reveal 分离；
* Challenge Reveal 必须由用户主动触发；
* 所有 Challenge 可换一个；
* Secret Match 不暴露任何一方具体拒绝内容；
* Hand-off Gate 不允许普通返回穿透；
* Session 完成一轮后不回首页；
* 媒体默认不进入系统相册；
* 管理型页面不侵入游戏主循环；
* 第一版不引入账号、社区、聊天和多人复杂模型。

## 3. 允许通过试玩调整的参数

* Bomb 爆炸分布；
* Fake Signal 频率；
* 触觉强度；
* 动效速度；
* RoundReady 时长；
* Next Move 出现频率；
* Challenge 重复窗口；
* 视觉主题色和具体品牌图形。

## 4. 变更证据

任何冻结项若要改变，需要至少满足一种：

* 真实试玩明确暴露阻塞；
* 可用性测试重复出现同一问题；
* 平台技术限制导致原方案不可实现；
* 审核/隐私/安全要求迫使调整。

不得以“开发更方便”“这个控件现成”“别的 App 都这么做”作为单独理由。

## 5. 每次版本评审输出

每次重大版本更新都应记录：

* 改了什么；
* 为什么；
* 哪条试玩证据支持；
* 是否影响三大核心资产：Secret Match / Suspense / Challenge Pack；
* 是否改变第一版的启动步数和单轮时长。
