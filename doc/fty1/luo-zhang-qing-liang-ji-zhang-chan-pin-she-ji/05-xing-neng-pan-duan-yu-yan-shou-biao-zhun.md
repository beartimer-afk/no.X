# 05｜性能判断与验收标准

## 当前判断

手动记账、账本查询和本地规则分类的计算量不大，首版没有必要引入在线大模型或每笔联网查询工商行业。主要风险是长列表渲染、数据库索引、批量导入和错误的同步策略，而不是分类规则本身。

已使用 Python + SQLite 在合成数据上做参考测试。测试只说明简单规则和带索引查询的数量级，不包含 Outlook 网络请求、邮件 HTML 解析、真实分类准确率、HarmonyOS 原生 UI、数据库加密或手机功耗，因此不能作为鸿蒙真机成绩宣传。

## 当前参考结果

| 数据量       | 7 条规则批量分类 P95 | 首批 50 笔查询 P95 |  月度汇总 P95 |    一次性批量写入 |
| --------- | ------------: | ------------: | --------: | ---------: |
| 10,000 笔  |     13.136 ms |      0.138 ms |  0.331 ms |  25.359 ms |
| 100,000 笔 |    122.359 ms |      0.077 ms | 14.018 ms | 333.993 ms |

这些数值来自当前桌面容器的热缓存和合成数据，不能外推到具体手机。10 万笔对普通个人用户也属于压力档，不是首版典型规模。

## 鸿蒙真机初始目标

| 项目   | 目标                   | 测量方式                              |
| ---- | -------------------- | --------------------------------- |
| 点击反馈 | 100 ms 内出现按压反馈       | 中端鸿蒙真机，覆盖常用入口                     |
| 单笔保存 | P95 ≤ 200 ms         | 点击保存到本地数据库提交成功；失败不关闭表单            |
| 首屏查询 | P95 ≤ 300 ms         | 10 万笔、日期索引、首批 50 笔；不等待邮箱          |
| 列表滚动 | 60 Hz 基准帧预算约 16.7 ms | 连续滚动 30 秒，记录慢帧比例和最长停顿             |
| 批量导入 | 页面始终可响应              | 100、1,000、10,000 条分档，网络/解析/写库分别计时 |

## 实现约束

* App 启动先读本地账本，不等待邮箱同步。
* 金额存整数分；日期、类型和来源字段建立适当索引。
* 明细列表按需创建和复用，不一次性渲染所有记录。
* 邮件解析与批量分类放到后台任务，写库分批提交。
* 商家规则一次加载，本地缓存匹配结果。
* 滚动时不能重新拉取邮件或重新分类全部记录。
* 性能报告要区分网络时间、解析时间、数据库时间和 UI 更新时间。

参考：[OpenHarmony 按需列表渲染](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/ui/rendering-control/arkts-rendering-control-lazyforeach.md)与[TaskPool](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/arkts-utils/taskpool-introduction.md)。具体采用 Repeat 或 LazyForEach，需要根据项目最终 SDK 版本确认。
